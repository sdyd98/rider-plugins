# Codemap — 코드 파악 노트

라이더에서 C++ 파일을 열면, 그 파일에 대한 **코드 파악 노트**를 오른쪽 `코드맵` 툴윈도우에 보여줍니다.
노트는 AI(Claude Code)가 MCP 툴을 통해 작성하고, `.codemap/` 아래에 저장되어 재사용됩니다.

> **판단은 전부 AI가 합니다.** 플러그인은 100% 정확한 사실만 제공합니다 — 줄 수, `#include` 줄,
> `.h`/`.cpp` 짝, git 이력, 내용 해시. C++ 파싱·상속 추론·호출 그래프 같은 건 하지 않습니다.
> 이 프로젝트는 `.sln`으로 빌드되어 컴파일 데이터베이스가 없고, 5,800만 줄 규모의 매크로 많은 C++을
> 정규식으로 "파싱"하면 그럴듯하게 틀린 정보가 노트를 오염시키기 때문입니다.
> (xlsx-editor의 refs MCP 툴과 같은 원칙 — CLAUDE.md § "judgment-free rule")

## 쓰는 방법

1. 파일을 엽니다. 노트가 있으면 바로 보이고, 없으면 **미분석** 칩만 보입니다.
2. 궁금한 점이 있으면 **[질문 달기]** 로 적습니다 (선택 — 질문이 곧 분석 지시입니다). Enter 로 바로 실행됩니다.
3. **[노트 만들기]** — 플러그인이 **에이전트 CLI를 직접 실행**해서 그 자리에서 노트를 만듭니다. 아래
   `분석기`에서 **Claude Code / Codex** 를 고릅니다. **[물어보기]** 는 대화 탭을 엽니다 — 이름이 다른
   이유는 하는 일이 다르기 때문입니다: 하나는 노트를 **쓰고**, 하나는 **묻습니다**(그 답은 나중에 대화
   탭에서 노트로 접어 넣을 수 있습니다).
4. 패킷 흐름을 보고 싶으면 **`＋ 패킷 시퀀스`** — 요청할 때마다 흐름이 하나씩 쌓이고, 뷰어 탭에서
   단계별로 재생됩니다.

MCP 쪽에서 시키는 것도 그대로 됩니다 — Claude Code 에게 "PlayerSession.h 분석해줘" 라고 하면 `codemap_stat`
으로 사실을 받고 소스를 읽고 `codemap_write_note` 로 씁니다.

**요청을 쌓아두는 큐는 없습니다.** 무엇을 분석할지는 사람이 그때 정합니다 — 플러그인이 들고 있는 할 일
목록이 아니라. 큐가 있었지만 쌓인 것을 볼 화면이 없어서 반쪽이었고, 반쪽 기능을 완성하는 대신 없앴습니다.


## 신선도 — 코드가 바뀌면 알려줍니다

노트를 쓸 때 대상 파일들의 **내용 해시(sha256)** · 분석 날짜 · 그때의 HEAD 커밋을 함께 기록합니다.
파일을 열 때 해시를 다시 계산해서 다르면 배너가 뜹니다:

```
⚠ 분석 이후 코드가 변경됨 — 2026-07-26 분석, 이후 커밋 12개
```

수정 시각이 아니라 **내용**을 비교하므로, 건드렸지만 내용이 같은 파일은 여전히 **분석됨**이고,
고쳤다가 되돌린 파일은 다시 **분석됨**으로 돌아옵니다.

`codemap_list_stale`로 오래된 노트를 한꺼번에 찾아 재분석을 몰아서 돌릴 수 있습니다.

## 함수 단위 분석 — 앵커

실서비스 파일은 2천~6천 줄입니다. 파일 요약 한 문단으로는 여전히 막막해서, 노트에 **함수 목차**가 들어갑니다.

```jsonc
"functions": [
  { "name": "HandleLogin",
    "anchor": "void PlayerSession::HandleLogin(const uint8_t* body, size_t len) {",
    "purpose": "인증 → World 입장까지",          // 모든 함수 필수, 한 줄
    "thread": "IOCP 워커",                       // 이하 선택 — 그럴 만한 함수만
    "locks": ["m_sessionLock 획득"],
    "calls": ["AccountDb::LoadAccount", "World::Enter"],
    "effects": ["m_state를 Authenticating → Playing"],
    "gotchas": ["m_sessionLock을 쥔 채 Close → World::Leave로 들어갈 수 있다"] }
]
```

**줄 번호를 저장하지 않습니다.** 위에 한 줄만 추가돼도 틀어지기 때문입니다. 대신 시그니처를
**원문 그대로**(`anchor`) 넣고, 플러그인이 파일에서 그 문자열을 찾아 현재 줄을 구합니다.
`.h`/`.cpp` 양쪽을 다 뒤지므로 헤더를 열어도 `.cpp`의 정의를 찾습니다.

찾는 방식은 **실제 코드베이스의 모양을 견디도록** 되어 있습니다 — `.sln` 으로 연 프로젝트에서 함수 목차가
통째로 비는 문제를 겪고 고친 것들입니다:

- **여는 중괄호가 다음 줄에 있어도** 찾습니다 (Visual Studio 기본 스타일). 한 줄 안에서만 찾던 때는
  `) {` 까지 복사된 앵커가 어떤 줄에도 없었습니다.
- **시그니처가 여러 줄로 쪼개져 있어도** 찾습니다. 최대 4줄까지 이어 붙여 봅니다 — 그보다 멀리 흩어진
  조각을 모으면 엉뚱한 것과 맞을 수 있어 거기서 멈춥니다.
- **공백·탭·줄바꿈을 무시**하고 비교합니다. 탭 들여쓰기나 콤마 뒤 두 칸이 함수의 정체를 바꾸지는 않습니다.
- **UTF-16 파일**을 읽습니다. BOM 이 없으면 ASCII 옆의 0 바이트로 알아냅니다 — 레거시 코드페이지(CP949 등)는
  추측하지 않습니다. 그런 판단은 이 플러그인이 하지 않는 종류의 일입니다.
- 매치는 **그 줄 안에서 시작**해야 합니다. 안 그러면 시그니처 위의 빈 줄이 그 시그니처의 위치를 가로챕니다.

이 방식의 부수 효과가 본체만큼 중요합니다:

- **앵커를 못 찾으면 = 그 함수만 오래된 것.** 파일 해시로 노트 전체를 회색 처리하는 대신 그 행에만
  ⚠ 를 붙이고 점프를 막습니다 — 엉뚱한 줄로 뛰는 것보다 안 뛰는 게 낫습니다.
- 앵커가 여러 줄에 걸리면 `중복` 배지. 약한 앵커라는 뜻이니 AI가 더 긴 줄로 고쳐야 합니다.
- `codemap_write_functions` 응답이 `functionAnchors`로 각 앵커의 해석 결과를 돌려주므로, AI가 쓴 직후
  자기 앵커를 검증할 수 있습니다.

**규칙 두 가지** (툴 설명에도 박아뒀습니다):

1. **모든 함수에 `purpose` 한 줄** — 게터·생성자 포함. 목차에 구멍이 있으면 "분석이 안 된 건가, 별거
   아닌 건가"를 매번 의심하게 됩니다.
2. **선언 순서로** — 코드를 스크롤하며 옆에 맞춰 읽게 되니까요.

패널에서는 함수 이름을 클릭하면 **에디터의 그 줄로 점프**하고, 12개를 넘으면 이름 검색이 붙습니다.

## 코드맵 루트 — `.sln` 위치가 아니라 **git 작업 트리**

`.codemap/`이 놓이는 위치이자 모든 경로의 기준입니다. Rider의 `project.basePath`는 **연 솔루션이 있는
폴더**라서, `.sln`이 하위 폴더에 있으면(`build/`, `msvc/`, `examples/` …) 상위의 소스가 전부 "프로젝트
밖"이 되어 노트를 가질 수 없습니다. 그래서 `git rev-parse --show-toplevel`을 루트로 씁니다 —
어느 솔루션을 열든 저장소 하나당 스토어 하나가 유지됩니다. git 저장소가 아니면 `project.basePath`로
떨어집니다.

(실제로 imgui로 테스트하다 발견한 문제입니다. Rider가 `examples/imgui_examples.sln`을 자동으로
열어버려서 루트의 `imgui.cpp`가 전부 "밖"으로 나왔습니다.)

## 저장 구조

`.codemap/`은 **소스 트리를 미러링하되 디렉토리 단위로 묶습니다.** 5,800만 줄에서 파일당 노트를 만들면
JSON이 수십만 개가 되므로, 디렉토리 하나당 번들 하나입니다.

```
Source/Game/Net/PlayerSession.h   →  .codemap/Source/Game/Net.json   (키: "PlayerSession.h")
Source/Game/Net/PlayerSession.cpp →  같은 노트 (짝은 노트 하나를 공유)
main.cpp (루트)                    →  .codemap/_root.json
```

- **`.h`/`.cpp` 짝은 노트 하나를 공유**합니다. 짝 판정은 기계적입니다 — 같은 디렉토리, 같은 base 이름,
  한쪽은 헤더 확장자(`h/hpp/hxx/hh/inl`), 한쪽은 소스 확장자(`cpp/cc/cxx/c`). 헤더가 있으면 헤더가 키.
- **로컬 전용**입니다. `.codemap/.gitignore`에 `*`를 써서 스스로를 무시하므로, 프로젝트의 `.gitignore`를
  건드리지 않고도 커밋에 절대 올라가지 않습니다.
- 스토어 자체 파일은 `_root.json`(루트 파일들의 번들) 하나이고, 이름으로 정확히 판정합니다. `_` 접두사로
  거르지 않습니다 — 소스 디렉토리 이름이 `_demo`일 수도 있고, 그 번들 `_demo.json`은 엄연히 노트이기
  때문입니다. `_pending.json`(옛 버전의 대기 큐)도 계속 건너뜁니다 — 큐는 없어졌지만 그때 만들어진 파일이
  남아 있는 `.codemap/`이 있고, 그걸 노트 번들로 읽으면 안 됩니다.

## 노트 스키마

노트는 **느슨한 JSON**입니다. 플러그인은 아래 키들을 렌더링하지만, 모르는 키는 그냥 무시하고 저장합니다 —
스키마를 AI가 키울 수 있고, 그때마다 플러그인을 다시 릴리스할 필요가 없습니다.

| 키 | 형태 | 내용 |
|---|---|---|
| `purpose` | string | 이 파일이 뭐 하는 놈인지 2~3줄 |
| `roleInSystem` | string | 서버 아키텍처 어디에 앉아있는지 |
| `classes` | `[{name, role}]` | 이 파일의 클래스들과 각각의 역할 |
| `entryPoints` | `[{symbol, note}]` | **여기부터 읽어라** — 순서대로 |
| `keyState` | `[{member, note}]` | 중요한 멤버 변수와 그 의미 |
| `threading` | `{model, affinity, locks: [{name, guards, order}]}` | 어느 스레드에서 뭐가 도는지, 락 순서 |
| `packets` | `[{id, dir, handler, sentBy}]` | 패킷 ID ↔ 핸들러. `dir`은 `"in"`/`"out"` |
| `dependsOn` | `[{target, why}]` | 의존하는 것과 그 이유 |
| `usedBy` | `[{source, context}]` | 이걸 쓰는 쪽과 그 맥락 |
| `flows` | `[{name, steps}]` | 시나리오. `steps`가 문자열 배열이면 **플로우차트**, `{from,to,call,kind}` 객체 배열이면 **시퀀스 다이어그램**으로 그려집니다. § "시퀀스 다이어그램" — 요청 단위로 누적됩니다 |
| `dataSources` | `[{kind, ref, note}]` | 읽는 게임 데이터/설정/프로토콜. `kind`는 `xlsx`/`db`/`config`/`proto` |
| `gotchas` | `[string]` | 함정, 호출 순서 제약, 수명 문제 |

`files` · `hashes` · `analyzedAt` · `analyzedCommit`은 **툴이 직접 찍습니다.** AI가 넣어도 무시되고,
응답의 `ignoredKeys`로 알려줍니다. `_manual`(사람이 고친 필드의 기록)도 플러그인 것이라 AI가 쓸 수 없습니다 —
써도 떼어냅니다. § "재분석은 덮어쓰기가 아닙니다" 참고.

추측으로 칸을 채우기보다 **소스에서 확인한 것만 쓰고 나머지 키는 생략**하는 것이 원칙입니다.

## 화면 읽는 법

노트는 **읽는 것보다 훑는 것**을 목표로 배치했습니다.

- **고정폭 = 코드에서 찾을 수 있는 것.** `OnPacket`, `m_sendLock`, `ClientPacket::LoginReq`는 전부
  monospace입니다. 산문과 식별자가 섞이면 노트가 그냥 글 덩어리가 됩니다.
- **패널에는 노트만 있습니다.** 줄 수·파일 크기·include 개수·커밋 수 같은 통계는 일부러 뺐습니다 —
  노트를 읽는 사람에게 아무 판단도 주지 않으면서 자리만 차지합니다. 안 보여주므로 **계산도 하지
  않습니다**: 탭을 바꿀 때마다 `git log`를 돌리고 파일을 세는 비용이 5,800만 줄에서는 그냥 지연입니다.
  (그 사실들이 필요한 쪽은 AI이고, `codemap_stat`이 전부 제공합니다.)
- **여기부터 읽기는 번호가 붙습니다** — ①②③. 순서 자체가 정보이기 때문입니다.
- **패킷은 방향 배지** — `수신`(파랑) / `송신`(초록). 6줄이 표처럼 정렬됩니다.
- **락은 블록 단위** — 락 하나당 `🔒 이름` + `보호`/`순서` 2열.
- **주의는 amber 카드** — 버그를 막는 줄이라 가장 강한 대비를 씁니다.
- **함수 목록** — 이름 클릭 = 코드 점프. 위치를 못 찾은 함수는 회색 + ⚠ 로 내려앉고 클릭이 막힙니다.
- **캐럿 카드의 버튼은 [호출 그래프] 하나**입니다. 그래프와 사용처는 화면을 넓게 쓰는 일이라 탭으로 넘겼고,
  "누가 부르나"는 툴윈도우에서 `Alt+F7`이 더 나은 답입니다.
- **흐름은 그림으로** — 문자열 체인은 플로우차트, `{from,to,call}` 은 시퀀스 다이어그램(라이프라인·자기호출
  ·점선 반환). 참가자가 많으면 축소하지 않고 가로 스크롤합니다 — 읽히지 않는 그림이 들어맞는 것보다
  읽히는 그림을 옆으로 미는 게 낫습니다.
- **패킷 시퀀스 섹션은 이름 목록**입니다 — 재생은 탭에서 봅니다. 비어 있으면 섹션 전체가 **버튼 하나**로
  접힙니다. "시퀀스 0개"라는 제목은 할 말이 없다는 말만 하는 섹션이라서요.

### 화면에 한 번에 뭘 보여줄지

한 번 아무것도 없는 상태로 되돌린 뒤, **써보고 필요하다고 확인된 것만** 하나씩 올렸습니다. 지금 올라온 것:

- **커서를 따라** — 에디터 캐럿이 함수 안으로 들어가면 그 함수 카드가 나타납니다. 캐럿 바로 위의 앵커로
  판정하므로 파일을 다시 읽지 않고, 캐럿이 아무리 움직여도 비용이 없습니다.
- **주의** — 접히지 않고 항상 열려 있는 유일한 섹션입니다. 나머지는 누군가 찾아간 질문의 답이지만, 이건
  **찾아갈 줄 몰랐던 질문의 답**이라 접으면 정확히 필요한 순간에 숨습니다.
- **패킷** · **스레드 / 락** — 처음부터 중요하다고 정한 두 축.
- **함수 목차**, **패킷 시퀀스**.

나머지(`요약` · `진입점` · `클래스` · `핵심 상태` · `의존` · `데이터 연결`)는 **아예 그리지 않습니다.**
한동안 아무도 열지 않는 접힘 뒤에 들고 있었는데, "혹시 필요할까" 로 남긴 코드는 썩습니다. 데이터는 노트에
그대로 있고 MCP 툴도 그대로 읽습니다 — 필요해지면 위의 것들처럼 자기 섹션으로 돌아옵니다.
접힘 상태는 파일을 바꿔도 유지됩니다.
섹션 제목마다 accent 세로 바이고, 색은 전부 팔레트(`CodemapUi.kt`) 경유라 라이트/다크 모두 맞습니다.

## 대화 — 노트를 문맥으로

패널의 **`[대화]`** 가 그 파일에 대한 대화 탭을 엽니다. 노트가 문맥으로 먼저 들어가므로 "이 파일 뭐 하는
거야"부터 다시 시작하지 않습니다.

**터미널의 Claude Code 와 겹치지 않는 부분은 하나입니다: 답을 노트에 남길 수 있다는 것.**

가장 큰 것은 **`[이 대화로 노트 갱신]`** 입니다 — 지금까지의 대화를 문맥으로 붙여 **구조화된 분석을 다시
돌리고** 노트를 씁니다. 대화에서 알아낸 락 순서·함정·패킷 흐름이 그대로 `threading`·`gotchas`·`flows` 에
들어갑니다. 대화만으로는 `functions`·`anchor`·`packets` 같은 구조를 만들 수 없고(패널의 거의 모든 화면이
그 구조 위에 서 있습니다), 반대로 분석만으로는 사람이 캐묻지 않으면 안 나오는 것들이 있습니다. 둘을 잇는
버튼입니다. 답 아래
`[주의로 추가]` / `[함수 설명으로]` 를 누르면 그 문장이 노트에 들어가고, **사람이 쓴 것으로 기록**되어
(`_manual`) 다음 재분석이 덮어쓰지 않습니다. 남기는 것은 개발자의 판단이지 에이전트의 판단이 아니고,
스토어가 그렇게 취급합니다.

**대화 기록은 우리가 들고 있습니다.** 두 CLI 모두 세션 이어가기를 광고하지만 실제로 기억하는 건 하나뿐이라
확인했습니다:

| 엔진 | 네이티브 이어가기 | 방금 알려준 값을 물었을 때 |
|---|---|---|
| `claude -r <세션ID>` | 기억함 | `바나나37` |
| `codex exec resume <id>` | **기억 못함** | `알 수 없음` |

그래서 매 턴 대화 전체를 프롬프트로 다시 보냅니다. 두 엔진에서 똑같이 동작하고, CLI의 세션 저장 방식이
바뀌어도 영향받지 않으며, 문맥을 우리 기준으로 자를 수 있습니다(오래된 턴부터, 24,000자). 대가는 매 턴
재전송이고 프롬프트 캐시가 그 비용을 흡수합니다.

- **툴윈도우가 아니라 탭**입니다. 채팅은 입력창이 항상 떠 있어야 하는데, 그 패널의 텍스트 필드는 포커스를
  가져가 IDE 단축키를 삼킵니다.
- 권한은 분석과 **똑같이 읽기 전용**입니다. 대화가 분석보다 더 멀리 손댈 수 있다면 그건 조용한 권한 상승입니다.
- 기록은 **탭에만** 남고 `.codemap/` 에 쓰지 않습니다. 스토어는 코드에 대한 노트이지 대화록이 아닙니다 —
  남길 가치가 있는 것은 위 버튼으로 명시적으로 남깁니다.
- Enter 로 보내고 ⇧Enter 로 줄바꿈, 진행 중에는 `[중단]`.

## 패킷 — 이 파일이 다루는 ID

노트의 `packets` 표가 패널에 나옵니다. 세 가지가 한자리에서 답해집니다:

- **어떤 ID를 다루나** — `수신`/`송신` 배지 + ID
- **누가 처리하나** — 핸들러(또는 송신처)를 **클릭하면 그 함수로 점프**합니다. 앵커가 더 이상 안 맞으면
  회색으로 내려앉고 클릭이 막힙니다 — 엉뚱한 줄로 뛰는 것보다 안 뛰는 게 낫습니다
- **다른 곳은 어디인가** — 프로토콜은 공유되므로, **같은 ID를 기록한 다른 노트**를 `다른 곳: World.h 송신`
  으로 보여줍니다. "누가 2999를 보내나"는 이 저장소에서 자주 나오는 질문인데 지금까지 답할 방법이
  없었습니다(`PacketIndex`)

ID 비교는 **숫자로 정규화**합니다 — `ClientPacket::LoginReq (1001)` 과 `1001` 은 같은 프로토콜을 두 분석이
다르게 적은 것이고, 이걸 못 잇는 색인은 아무 답도 못 합니다. 16진수가 있으면 그것이 우선하고, 숫자가 아예
없으면 문자열 전체가 키입니다(두 노트가 똑같이 적어야 이어집니다 — 정직한 결과입니다).

그 ID를 추적하는 **패킷 시퀀스가 있으면 링크**가 붙습니다. 표와 시퀀스가 서로를 가리키면 두 기능이
하나가 됩니다.

## 패킷 시퀀스 — 요청한 것이 쌓이고, 단계별로 재생됩니다

**`＋ 패킷 시퀀스`** 에 시나리오를 한 줄로 적고 `[그리기]`(또는 Enter) — "로그인 패킷부터 월드 입장
통보까지". 답이 오면 `패킷 시퀀스` 섹션에 이름이 하나 **추가**되고, 클릭하면 **뷰어 탭**이 열립니다.

### 뼈대는 패킷입니다

게임 서버에서 추적할 가치가 있는 순서는 패킷 순서입니다. 그래서 요청은 **받은 패킷에서 시작해서 그
패킷이 유발하는 패킷들을 따라가는** 것으로 좁혀져 있습니다.

- 패킷 단계는 `packet` 에 **코드에 있는 상수 이름을 원문 그대로** 씁니다 (`ClientPacket::LoginReq`).
  이름을 만들어내지 않습니다.
- `id` 는 코드가 값을 주는 경우에만 (`1001`, `0x81`). 없으면 생략합니다 — 추측한 ID는 없는 것보다 나쁩니다.
- **방향은 `from`/`to` 로 드러납니다.** 서버→클라이언트 패킷은 "반환"이 아니라 반대 방향 패킷입니다.
- **패킷 사이의 내부 처리는 한 줄씩만** — 다음에 어떤 패킷이 나가는지를 바꾸는 것만 넣습니다(검증 실패로
  끊김, DB 조회 결과에 따른 분기, 상태 전이). 이게 없으면 시퀀스가 아니라 패킷 목록이 됩니다.
- 패킷이 하나도 없는 시나리오면 빈 배열이 옵니다. 억지로 만들지 않습니다.

화면에서 패킷 단계는 눈에 띕니다 — 번호 알약이 **채워지고**(사이 단계는 비어 있음), 패킷 상수가 고정폭
굵은 글씨로, `id` 가 오른쪽 배지로 붙습니다. 그래프 카드에서도 패킷 행의 배지는 순번이 아니라 **패킷 ID**
입니다.

### 라이프라인 차트가 아니라 재생기입니다

[IcePanel의 Flows](https://docs.icepanel.io/visual-storytelling/flows) 모델을 따랐습니다. 그쪽 주장이
설득력 있었습니다 — 라이프라인 차트는 시스템의 **두 번째 그림**이라 따로 읽어야 하고 첫 번째 그림과 계속
맞춰야 하는데, 흐름은 **이미 있는 다이어그램 위를 지나가는 순서 있는 경로**입니다. 코드베이스를 파일 단위로
익히는 중이라면 "호출이 이동하는 걸 보는 것"이 "그 차트를 읽는 것"보다 낫습니다.

- **왼쪽에 번호 단계 카드**, 활성 단계는 accent 테두리. 클릭하면 그 단계로 바로 갑니다(비선형 이동).
- **오른쪽은 참가자 그래프** — 호출 그래프와 **같은 캔버스**(`:common`)입니다. 흐름과 호출 그래프가 한
  제품처럼 보이는 게 목적입니다.
- **스포트라이트**: 활성 단계의 엣지가 굵어지고 양쪽 카드에 accent 링이 붙고, **나머지는 30%로 흐려집니다.**
  숨기지 않고 흐리는 건 주변이 그 단계를 의미 있게 만드는 문맥이기 때문입니다.
- **소개 단계**로 시작합니다 — 전체가 보이고 아무것도 강조되지 않은 상태. 걷기 전에 장면을 세우는 것입니다.
- `◀` `▶` `처음으로`, 그리고 **←→↑↓ / Space**.
- **`시퀀스 차트` 토글** — 라이프라인 차트도 남겼습니다. 같은 단계를 다르게 읽는 것이지 다른 진실이 아니고,
  남에게 넘길 그림으로는 차트가 낫습니다. (IcePanel 사용자들도 같은 것을 요청하고 있습니다.)
- **삭제는 뷰어에 있습니다.** 무엇을 지우는지 볼 수 있는 유일한 곳이라서요 — 이름만 있는 행에서 지우게
  하면 안 됩니다.
- 탭은 **하나만** 씁니다. 다른 흐름을 열면 같은 탭이 그것으로 바뀝니다 (호출 그래프와 같은 이유).

### 단계 타입

`steps[].kind` 로 밝힙니다. **`packet` 이 있으면 그것이 결정합니다**(선언된 `kind` 보다 우선 — 옛 노트가
`{packet, kind:"return"}` 으로 적어둔 것도 반대 방향 패킷으로 읽힙니다). 나머지는 선언되지 않았으면
**기록된 값에서 산술로** 도출합니다 — 라벨의 문장을 읽고 추측하지 않습니다.

| `kind` | 뜻 | 그림 |
|---|---|---|
| — (`packet` 있음) | **패킷 교환** — 이 시퀀스의 뼈대 | 채운 번호 알약 + ID 배지, 양쪽 카드 강조 |
| (생략) | A가 B를 호출 (패킷 사이를 잇는 단계) | 실선 + 채운 화살촉 |
| `return` | 값이 돌아옴 | 점선 + 열린 화살촉 |
| `process` | 한 객체가 혼자 하는 일 | 그 카드 하나만 강조 (엣지 없음) |
| `note` | 객체와 무관한 설명 한 줄 | 단계 카드만, 그림에는 아무 영향 없음 |

**`description`** 은 그 단계가 왜 일어나는지 한 문장이고 **단계 목록에만** 나옵니다. `call` 이 "무엇을"이면
`description` 은 "왜"입니다. 캔버스에 산문을 올리면 그림과 싸우기 때문에 나누었습니다.

한쪽 끝이 없거나 양끝이 같은 단계는 `process` 로 읽힙니다. 그래서 **예전 노트가 그대로 열립니다** — 자기
호출로 적어둔 단계들이 자동으로 맞는 타입이 되고, 옛 문자열 체인(`steps: ["OnPacket", …]`)은 `note` 가 됩니다.
없는 참가자를 만들어내지 않습니다.

**아직 없는 것**: `alt`/`loop` 같은 **분기 경로**(IcePanel의 Alternate / Parallel paths). 스키마에 분기
개념을 넣고 프롬프트·파서·렌더러를 다 고쳐야 하는 일입니다.

### 누적이 핵심입니다

이 흐름들은 생성된 것이 아니라 **모은 것**입니다 — 하나하나 사람이 이름을 붙여 요청했기 때문에 존재합니다.

- 저장은 **이름 기준 upsert**(`writeFlows`)입니다. 다섯 번째를 요청했다고 앞의 네 개를 잃으면 안 됩니다.
- **같은 이름으로 다시 요청하면 그 하나만 교체**됩니다. 결과가 틀렸을 때 다시 물어보는 방법입니다.
- **파일 전체 재분석도 모아둔 흐름을 지우지 않습니다.** `flows`는 `functions`와 같은 병합 규칙을 따릅니다
  (§ "재분석은 덮어쓰기가 아닙니다").

프롬프트도 **시나리오 하나로 좁혀서** 보냅니다. 노트 전체 스키마를 주지 않고 `{flows:[…]}` 만 요구하고,
이미 있는 흐름 이름들을 알려주며 "이것들을 다시 만들지 마라"고 말합니다. 질문 하나의 부수 효과로 에이전트가
노트 나머지를 다시 판단하게 만들지 않기 위해서입니다.

MCP 쪽에서는 `codemap_write_flows`로 같은 upsert를 씁니다 — 일괄로 여러 흐름을 만들어도 서로를 지우지
않습니다.

## 호출 그래프 — 공용 캔버스

**[호출 그래프]** 는 에디터 탭 하나를 열고, 노트들이 이미 기록해둔 호출 관계를 그립니다. 위가 호출자,
가운데가 지금 함수, 아래가 피호출자입니다.

그림은 xlsx-editor 관계도와 **같은 캔버스**(`:common`의 `com.example.graph.GraphCanvas`)로 그립니다.
같은 저장소에 두 개의 그래프 렌더러를 두는 것은 둘 중 하나가 반드시 뒤처진다는 뜻이라, 카드 그리기·배치·
조작을 공용으로 뺐습니다:

- **노드는 카드입니다.** 제목(함수 전체 이름) + 파일명, 그 아래 노트에 있는 것이 행으로 — `· 요약` /
  `⇄ 스레드` / `🔒 락` / `→ 호출 대상`(배지 = 대상이 있는 파일).
- **폭을 실측합니다** (`TextMeasurer`) — 이름이 `…`로 잘리면 그래프가 답을 못 하니까요. 단 한 줄에 상한이
  있습니다: 노트가 참가자 자리에 문장을 적어두는 일이 있고, 그 한 장이 카드를 거대하게 만들면 맞춤이 그림
  전체를 30%까지 줌아웃시킵니다. 드문 긴 라벨에 말줄임 하나를 쓰고 나머지 카드의 가독성을 지킵니다.
- **호출 행에 hover** 하면 그 엣지가 강조되고 도착 카드에 링이 생깁니다. 카드에 hover하면 그 카드를 지나는
  모든 엣지가 살아납니다.
- **pan / zoom / 맞춤 / 재배치**, 노드 드래그, 곡선 엣지 + 화살촉, 점 배경.
- **배치는 랭크 방식**입니다 — xlsx가 쓰는 force 배치를 여기서는 쓰지 않습니다. 위/아래가 **의미**(누가
  누구를 부르는지)라서 유기적으로 흩으면 그 의미가 사라집니다. 랭크 안의 순서만 연결 상대의 평균 위치로
  두 번 정렬해서 엣지 교차를 줄입니다.
- 배치 계산은 **오프스레드**입니다. O(n²)를 컴포지션 안에서 돌리면 EDT가 초 단위로 멈춥니다.

탭은 **하나만** 씁니다. 다른 함수의 그래프를 열면 같은 탭이 그 함수로 재중심됩니다 — `LightVirtualFile`은
동일성으로 비교되므로 클릭마다 새 파일을 만들면 같은 이름의 탭이 쌓입니다. 그래프는 들여다보는 자리이지
모아두는 문서가 아닙니다.

**이 그래프의 의미는 정확히 하나입니다: 노트가 말하는 것, 분석된 파일에 대해서.** 전수 조사가 아니고,
헤더가 그렇게 적어둡니다. 분석되지 않은 이름(어떤 노트가 `calls`에만 적어둔 것)은 흐리게 그리고 클릭이
막힙니다 — 목적지가 아닌 것을 목적지처럼 보이게 하지 않기 위해서입니다.

## 사용처 찾기 — 라이더가 찾고, 우리가 보여줍니다

그래프 탭의 **[사용처 찾기]** 는 그 함수가 실제로 호출되는 곳을 캔버스 아래 목록으로 채우고, 줄을 클릭하면
그 위치로 점프합니다. 라이더의 Find 창을 여는 게 아닙니다 — 창은 액션의 부수 효과일 뿐이고, 결과를 읽은 뒤
다시 닫습니다.

**툴윈도우에는 이 버튼이 없습니다.** 거기서는 `Alt+F7`이 더 나은 도구입니다 — 트리 그룹화·필터·미리보기가
있고, 캐럿은 이미 그 함수에 있습니다. 이 기능이 버튼을 얻을 만한 곳은 그래프 탭 하나입니다: 그래프는
*노트가 아는 것*이고 이 목록은 *백엔드가 아는 것*이라, **둘의 대비를 한 화면에서 보는 것**이 유일한 이유입니다.
(다른 파일에 있는 노드를 그 파일을 열지 않고 물어볼 수 있다는 것도 여기서만 생기는 이점입니다.)

프론트엔드에는 C++ PSI가 없습니다. C++ 의미 정보는 전부 ReSharper 백엔드에 있고, "이 심볼 어디서 쓰나"를
직접 물을 수 있는 프로토콜 호출도 노출돼 있지 않습니다. 대신 이렇게 합니다:

1. 앵커로 구한 줄에 캐럿을 놓고 (`::` 뒤 이름의 컬럼까지 맞춰서),
2. 라이더 자신의 `FindUsages` 액션을 실행하고,
3. 결과가 담기는 플랫폼 `UsageView`를 폴링해서 읽습니다. 원소들은 `Usage` · `UsageInFile` ·
   `UsageInfoAdapter` · `Navigatable`을 구현합니다 — **전부 공개 플랫폼 인터페이스**라서, 의존하는 대상은
   Rider의 사설 클래스 모양이 아니라 Rider가 채워 넣는 계약입니다.

이 경로에서 실제로 문제였던 것들과 각각의 대응:

- **사용처가 딱 하나면 라이더는 목록을 만들지 않고 바로 점프합니다.** `FindSettings.isSkipResultsWithOneUsage
  = false`로도 안 막힙니다(Rider의 C++ 경로가 안 봅니다). 그래서 **점프 자체를 답으로 읽습니다** — 캐럿을
  놓은 위치와 지금 위치가 다르면, 그 도착지가 곧 유일한 사용처입니다. 위치는 IDE가 실제로 착륙한 곳이고
  텍스트는 그 줄의 문서 내용이므로, 여기서 추측하는 건 없습니다.
- **검색이 사람을 움직이면 안 됩니다.** 캐럿을 심볼로 옮기는 것도, 단일 사용처로 점프하는 것도 에디터를
  움직입니다. 그래서 **아무것도 건드리기 전에** 원래 에디터·캐럿을 기억해두고, 결과를 읽은 뒤 되돌립니다.
- **선언 줄은 결과에서 뺍니다.** "어디서 쓰나"를 물었는데 자기 자신이 답에 있으면 개수가 틀립니다.
- **파일은 루트 기준 상대 경로로 묶습니다.** 5,800만 줄에서 `World.cpp`는 하나일 수 없습니다.
- **30초까지 기다립니다**(400ms × 75). 8초는 장난감 프로젝트에서만 충분했습니다. 실패는 거의 항상
  "인덱싱이 아직"이라서 **[다시 시도]** 버튼이 곧 해결입니다.

## 플러그인이 에이전트를 직접 실행 — `[분석 실행]`

MCP는 "AI가 IDE를 호출하는" 방향입니다. 반대 방향도 됩니다: 플러그인이 CLI를 헤드리스로 실행해서 노트를
받아옵니다. 요청 박스 아래 **`분석기  [Claude Code] [Codex]`** 로 고르고, 선택은 설정에 남아 다음 파일에도
유지됩니다. 설치를 못 찾으면 프로세스를 띄우기 전에 그 자리에서 `설치를 찾지 못함`이라고 말합니다.

```
claude -p --allowedTools Read Grep Glob --output-format json     # 프롬프트는 stdin
codex exec -s read-only --skip-git-repo-check --color never -o <임시파일> -   # 프롬프트는 stdin
```

**프롬프트는 명령줄이 아니라 stdin 으로 갑니다.** `-` 로 시작하는 인자는 옵션이고, 노트 텍스트는 무엇으로든
시작할 수 있습니다 — `-1의 값을 반환한다` 로 시작하는 gotcha 하나가 프롬프트 전체를 파서로 삼켜버려
`error: unknown option '-1의 …'` 로 죽었습니다. 두 CLI 모두 이 이유로 stdin 을 공식 지원하고, 덤으로 인자
길이 상한도 사라집니다.

- **프롬프트는 두 엔진이 완전히 같습니다** (`NoteRequest`). 어느 쪽이 썼는지가 노트에 드러나면 안 됩니다.
  엔진별로 다른 것은 실행 파일 찾기 · 인자 · 답이 나오는 위치 세 가지뿐입니다(`AgentCli` 인터페이스).
- **쓰기 권한을 주지 않습니다.** Claude는 읽기 툴만 허용하고, Codex는 `-s read-only`로 **샌드박스 수준**에서
  막습니다. 노트를 쓰는 것은 언제나 플러그인이므로 "분석이 돌았다"와 "노트가 바뀌었다"가 별개 사건으로
  남고, 사이에 파싱 검증이 들어갑니다.
- **답을 읽는 방식**: Claude는 stdout을 감싼 envelope(`result`/`session_id`/`is_error`/`total_cost_usd`)를
  벗겨내고, 그것이 또 envelope처럼 보이면 거부합니다(세션 id로 가득한 "노트"가 디스크에 앉는 걸 막습니다).
  Codex는 `-o` 파일에 **마지막 메시지만** 나오므로 진행 로그와 섞이지 않습니다.
- **MCP는 안 씁니다.** 그 CLI의 MCP 설정이 어느 IDE를 가리킬지 모르고, 파일 읽고 답하는 데는 필요 없습니다.
- 실행 파일은 **통상 설치 위치 → `PATH`** 순으로 찾고, 설정의 `claudePath`/`codexPath`로 직접 지정할 수도
  있습니다. (GUI로 띄운 IDE는 로그인 셸의 `PATH`를 물려받지 않으므로 위치 탐색이 먼저입니다.)
- 타임아웃 10분, 실행 중에는 **[취소]** 가 뜹니다. 실제 프로젝트에서는 커피 한 잔짜리 작업입니다.

### 함수 하나만 — `[이 함수만 재분석]`

캐럿 카드의 버튼입니다. 6천 줄 파일을 통째로 다시 돌리는 것은 몇 분이 걸리고, 대개 궁금한 것은 함수
하나입니다.

요청도 답도 **좁습니다**: 프롬프트가 그 함수의 현재 내용만 보내고 `{"functions":[…]}` 만 요구하며, 저장은
`writeFunctions`(이름 기준 upsert)로 갑니다. `writeNote`로 보내면 **받은 객체를 노트 전체로 취급해서**
답이 되풀이하지 않은 키(요약·패킷·스레드)를 전부 날립니다 — 좁은 질문의 부수 효과로 노트를 잃는 셈입니다.

### 재분석은 덮어쓰기가 아닙니다

`[재분석 실행]`이 사람이 쓴 것을 지우면 그 기능은 못 쓰는 기능입니다. 세 겹으로 막습니다.

**1. 기존 노트를 프롬프트에 실어 보냅니다.** "다시 써라"가 아니라 "이것을 고쳐라 — 코드와 달라진 부분만
바로잡고, 여전히 맞는 내용은 그대로 다시 내보내라, 확인해서 틀린 게 아니면 지우지 마라"입니다. 노트가
12,000자를 넘으면 함수의 깊은 필드(`calls`/`effects`/…)를 접고 `name`·`anchor`·`purpose`는 전부 유지합니다
— 무엇이 존재하는지는 알아야 절반을 조용히 잃지 않습니다. 출처와 `_manual` 값은 보내지 않습니다.

**2. `functions`는 이름 기준 upsert입니다.** 이번 분석이 언급하지 않은 함수는 남습니다. 40개 중 10개만
답했다고 나머지 30개가 사라지면 안 됩니다.

**3. 사람이 고친 필드는 `_manual`에 따로 기록되고, 저장의 맨 마지막에 다시 덮입니다.**

```jsonc
"_manual": { "purpose": "내가 고친 요약",
             "functions": { "HandleLogin": { "purpose": "내가 고친 설명" } } }
```

`writeNote` 순서: 들어온 노트에서 `_manual`·출처 키를 떼어내고(AI가 사람 흉내를 낼 수 없습니다) →
`functions` upsert → **`_manual` 덮어쓰기** → `_manual` 자체를 다음 세대로 넘김(그 다음 재분석도 같은
구속을 받습니다). 핀은 **고친 필드에만** 걸립니다: 함수 `purpose`를 고쳤으면 `purpose`만 지켜지고
`thread`·`calls`는 분석이 계속 갱신합니다. 타이핑은 사람에게 비싸고 에이전트에게는 몇 초라서, 둘이
다투면 사람이 이깁니다.

편집이 있는 노트는 헤더에 **`수정됨`** 칩이 붙습니다. 그리고 편집은 출처를 **다시 찍지 않습니다** —
문장을 다듬은 것은 재분석이 아니니까요.

## MCP 툴

IDE 내장 MCP 서버(Settings | Tools | MCP Server → **Enable MCP Server**)에 등록됩니다. 전부 JSON 텍스트를
반환하고, 경로는 코드맵 루트 기준 상대 경로입니다(절대 경로도 받아서 정규화).

**대상 프로젝트는 MCP 프레임워크가 정합니다.** 툴에 `root` 같은 인자가 없습니다 — IDE의 MCP 서버가
호출마다 대상 프로젝트를 결정하고, 애매하면 클라이언트에게 `projectPath`를 요구합니다. 플러그인은
`currentCoroutineContext().project`로 그 결과를 그대로 받습니다.

| 툴 | 하는 일 |
|---|---|
| `codemap_stat` | 줄 수·크기·`.h`/`.cpp` 짝·`#include` 줄·git 이력·노트 유무/신선도 |
| `codemap_find_mentions` | 심볼 문자열이 **문자 그대로** 등장하는 파일과 줄 번호 (grep이지, 참조 검색이 아님) |
| `codemap_read_note` | 저장된 노트 읽기 |
| `codemap_write_note` | 노트 저장 + 출처 기록 |
| `codemap_write_functions` | 함수 목록에 **이름 기준 upsert** — 큰 파일을 몇 개씩 나눠 분석해도 이미 쓴 게 안 날아갑니다. 응답에 앵커 해석 결과 포함 |
| `codemap_write_flows` | 시퀀스 다이어그램 **이름 기준 upsert**. `flow`가 붙은 요청에 답하는 유일한 툴이고, 노트의 나머지는 건드리지 않습니다 |
| `codemap_list_stale` | 분석 이후 내용이 바뀐 노트 목록 (+ 이후 커밋 수) |

### 툴이 하지 않는 것 (의도된 것)

- `#include` 목록은 **텍스트 그대로**입니다. `#if`/`#ifdef` 안의 줄도 그대로 나오고, 매크로로 만든
  include 경로는 해석하지 않습니다. **이것을 의존성 그래프로 취급하지 마세요** — 의존성은 코드를 읽고
  직접 판단해야 합니다.
- `codemap_find_mentions`는 주석·문자열·무관한 이름도 잡고, typedef나 매크로를 거친 실제 참조는
  **놓칩니다**. 히트 하나하나를 직접 판단해야 합니다.
- 상속·호출 그래프·클래스 경계·역할 — 전부 툴이 제공하지 않습니다.

## MCP 툴 직접 호출해보기 (개발용)

MCP 서버를 켜면 IDE가 `127.0.0.1:64342/sse`로 SSE 엔드포인트를 엽니다. Claude Code를 거치지 않고
JSON-RPC로 바로 두드려볼 수 있습니다 — `initialize` → `tools/list` → `tools/call`.

이때는 인자에 **`projectPath`를 넣어야 합니다.** 프로젝트가 하나만 열려 있어도 그렇습니다 — 프레임워크는
클라이언트가 알려준 작업 디렉토리로 대상을 고르는데, 직접 만든 클라이언트는 그걸 안 보내기 때문입니다.
Claude Code는 cwd를 보내므로 보통 생략됩니다.

## 빌드

```bash
./gradlew :codemap:buildPlugin   # -> codemap/build/distributions/codemap-<ver>.zip
./gradlew :codemap:test          # 경로 매핑 / 짝 판정 / include 추출

# 실제 C++ git 저장소에 대고 사실을 검증 (wc -l / shasum / git 실측치와 대조)
./gradlew :codemap:test -Dcodemap.testRepo=/path/to/cpp/repo

# 샌드박스 IDE를 특정 프로젝트와 함께 띄우기
./gradlew :codemap:runIde -PrunIdeProject=/path/to/cpp/project
```

동작하는 것: 노트 표시(캐럿 추종), 함수 목차 + 코드 점프, 패널 내 노트 편집 — **재분석이 그 편집을 지우지
않음**, 공용 캔버스로 그리는 호출 그래프 + 그래프 탭 내 사용처 목록(라이더 Find Usages 기반), **요청 단위로 누적되고
